# MyClass Windows 客户端

这个客户端把 Windows 的整个显示器或单个应用窗口画面，以及系统输出声音，通过 WebRTC 推送到现有 MyClass 教室大屏。它复用仓库已有的连接码、WebSocket 信令、TURN 配置和浏览器接收端，不新增媒体中转服务器。

## 技术方案

- Electron + Chromium WebRTC：使用系统硬件编码能力，避免在 Windows 端重新维护 WebRTC 原生封装。
- Electron 主进程使用 `ws` 连接现有 `/myclass/ws`，作为 `teacher` 角色发送 `teacher.join`、`webrtc.offer` 和 ICE candidate。这样不受 `file://` Origin 校验影响。
- 渲染进程使用 `getDisplayMedia` 采集选定显示器或应用窗口；主进程通过 `desktopCapturer` 枚举来源，并在 Windows 上将 Electron 的 `loopback` 音频源绑定到同一个共享流。
- 视频按 30 FPS、最高 16 Mbps 发送，并设置 `contentHint=text`、`scaleResolutionDownBy=1` 和 `degradationPreference=maintain-resolution`：屏幕文字属于高细节内容，局域网下放开码率可以明显提升文字锐度；带宽不足时优先降帧率而不是降分辨率，避免画面整体变糊。带宽估算（GCC）会在弱网时自动降回可用码率，不会因此拥塞。
- 采集上限为 2560 宽（16:9 屏幕即 2560×1440，高度始终跟随屏幕原始比例；采集端只会向下缩放、不会放大，1080p 笔记本仍按原分辨率采集）：原实现统一封顶 1920×1080，在 1080p 大屏上确实更锐利，但 4K 大屏会在显示端把 1080p 拉伸放大，文字随之发虚。注意不要同时限制宽和高，Chromium 会按固定宽高比 `crop-and-scale` 裁掉屏幕内容（实测 3840×2160 会被裁成 2560×1600）。90Hz 等高刷新率屏幕不受影响（采集帧率固定 30 FPS）。
- 强调鼠标位置：投屏时屏幕上显示一个红色光标点（外圈已按课堂反馈去掉，只保留中心强调点），方便远处学生看清鼠标位置。显示器投屏使用全屏透明置顶覆盖层（光标点在覆盖层内跟随鼠标绘制，随画面一起被采集；覆盖层窗口自身固定不动，可避免部分电脑在投屏采集时标记向右下漂移）。单应用窗口投屏时覆盖层不属于窗口内容、无法被采集，因此改为发送端合成：把采集帧逐帧绘制到 canvas，按主进程推送的光标位置（屏幕 DIP 坐标相对窗口/显示器区域归一化，再乘以帧分辨率；点的直径按「帧像素 ÷ 区域 DIP 宽度」换算，保证与覆盖层模式在大屏上大小一致）把光标点画进画面后经 `canvas.captureStream` 发送，大屏看到的点与画面内指针位置对齐。开始前可勾选/取消，投屏中可点击"关闭/开启鼠标强调"按钮或托盘菜单切换。
- 连接自愈：本端持续检测出帧与信令状态，发现大屏画面停住时自动重建合成流、必要时重新采集并重新协商，详见下文“连接稳定性”。
- 主进程创建系统托盘。关闭窗口只隐藏到托盘，点击托盘图标或使用“切换投屏窗口”菜单可直接选择新的显示器/应用窗口；右键菜单还可以停止投屏或退出程序。投屏时窗口隐藏到托盘后，托盘提示文字会同步显示“正在投屏 / 正在自动恢复 / 大屏断开，等待自动恢复”，老师不必打开面板也能知道当前状态。

## 连接稳定性

课堂上出现的“大屏画面不动了，但 Windows 端显示仍然已连接”，主要来自四类原因，客户端现在都能自动发现并恢复：

| 现象 | 原因 | 客户端的处理 |
| --- | --- | --- |
| 大屏刷新页面、浏览器重启、切换网络后一直黑屏/停在最后一帧 | 房间在 5 分钟宽限期内复用原连接码，大屏恢复了 WebSocket，但它那一侧的 `PeerConnection` 已经销毁，必须由教师端重新发 offer | 收到 `viewer.online` 后自动重新协商 |
| Wi-Fi 漫游、交换机抖动、休眠唤醒后画面卡住 | ICE 通道失效，Chromium 只会停在 `disconnected` / `failed`，不会自行恢复 | 状态变化 4 秒内未恢复或直接 `failed` 时自动重新协商 |
| 连接仍是 `connected`，但大屏定格 | 编码器或强调点合成画布停止出帧（隐藏到托盘后画布不再重绘等） | 每 3 秒用 `getStats` 检查出帧数与发送字节，连续 6 秒不增长即判定卡死并自动重建 |
| 采集轨结束（显示器休眠、切换显卡输出、窗口被销毁） | 采集已停止，本端却仍在发送旧帧 | 恢复时检测轨道状态，必要时重新采集 |

自动恢复的步骤是：重建强调点合成流（如启用）→ 采集轨已结束时重新采集 → 重建 `PeerConnection` 并重新发送 offer。为避免误判和抖动，做了以下约束：

- 大屏不在线（收到过 `viewer.reconnecting`）时不做媒体层恢复，等 `viewer.online` 后由信令触发，避免 offer 发进空房间。
- 两次自愈之间至少间隔 8 秒；连续自愈 4 次仍未成功则停止重试并提示“请点击停止投屏后重新开始”，不会无限循环。
- 连续正常出帧 20 秒后重置自愈计数。
- 发出 offer 7 秒仍未连上时，先原样重发 2 次（大屏可能刚好在刷新页面），再进入上述自愈流程。
- `join.accepted` 与 `viewer.online` 通常同一批到达，只保留一次协商，避免连发两个 offer 导致 answer 落到错误的连接上。

信令通道也加了保活：客户端每 5 秒发一次 `client.ping`，20 秒收不到任何消息即判定为半开连接（网线被拔、AP 重启后 TCP 可能仍是 ESTABLISHED），主动断开并走重连；服务端原有 15 秒 ping / 45~60 秒判死的心跳保持不变。

## 开发运行

需要 Windows、Node.js 20+ 和可访问现有 MyClass 服务端的网络环境：

```powershell
cd windows
npm install
npm start
```

输入大屏显示的 4 位连接码，选择要共享的显示器或应用窗口并点击“开始投屏”。如果应用是在客户端启动后才打开的，点击“刷新”更新窗口列表。首次共享时 Windows 可能显示屏幕采集确认。投屏建立后控制面板会自动隐藏到系统托盘。

选择应用窗口后只发送该窗口画面，不会发送其他窗口；音频仍来自 Windows 系统回环，因此其他应用同时播放的声音也可能被发送。应用窗口关闭时客户端自动停止投屏；窗口最小化时是否继续显示画面取决于 Windows 和目标应用的窗口捕获实现，客户端不会主动把最小化当作关闭。

设置页的“投屏时在笔记本电脑上同时播放声音”默认开启。关闭后，客户端会暂时静音 Windows 默认播放设备，但继续保留发送到大屏的音频轨；停止投屏、退出程序或程序异常重启后，会尝试恢复之前的静音状态。投屏过程中不需要打开主界面，点击系统托盘图标即可在不中断连接码和信令连接的情况下切换投屏窗口。

## 构建安装包

```powershell
cd windows
npm run check
npm run dist
```

安装包输出到 `windows/dist/`。正式部署前建议增加代码签名证书，否则 Windows SmartScreen 可能提示未知发布者。`electron-builder` 的 Windows 目标当前为 x64 NSIS 安装包。

## 声音说明

当前采集的是 Windows 默认播放设备的系统输出声音，例如课件视频、浏览器和播放器声音；不是麦克风。大屏网页端遵循浏览器自动播放策略，首次使用时如果没有声音，点击一次大屏页面或页面上的播放/声音控件即可解除静音。

如果系统策略、远程桌面会话或音频驱动不提供 loopback，客户端仍会发送视频，并在控制面板中显示“未获取到系统声音”。正式课堂部署建议在实际教室电脑上先播放一段带声音的视频完成验收。

不同声卡和驱动对 loopback 与系统静音的处理可能不同。如果关闭笔记本声音后大屏也没有声音，建议使用 VB-CABLE 等虚拟音频设备，将课件输出路由到虚拟设备，再由客户端采集该设备；当前版本还没有虚拟音频设备选择器。

## 单个应用投屏

客户端支持从“投屏来源”中选择单个应用窗口。该功能不需要修改服务端协议，应用窗口和显示器都使用同一条 WebRTC 链路。窗口列表来自 Electron 当前可捕获的窗口；某些管理员权限窗口、受保护内容或硬件加速画面可能无法捕获，这是 Windows 桌面采集的系统限制。

## 与现有服务端的联调边界

现有服务端已经允许 `teacher` 转发 `webrtc.offer`、`webrtc.answer` 和 `webrtc.ice-candidate`，网页大屏已经能接收音频轨和视频轨，因此不需要改信令协议。局域网直连优先；跨网段时继续使用服务端 `/api/config` 返回的 TURN 配置。

客户端目前按“一个连接码一个教师端”工作，与 Android 端规则一致：同一连接码连接新设备后，旧设备会被服务端踢出。
